The ShopSense data pipeline, file by file

A medallion pipeline that turns raw e-commerce event CSVs into a queryable star schema and a set of dashboard-ready views — four Cloud Functions, one BigQuery warehouse, three Pub/Sub handoffs. This covers everything through the Gold layer and its Looker Studio views; the GenAI/semantic-agent layer is intentionally out of scope.

GCS Bronze Staging Silver Gold Views

Overview & architecture

Every stage is one Cloud Function that treats BigQuery as the compute engine, not itself. A function's job is to decode a trigger, submit SQL, wait, and log what happened — never to hold rows in its own memory. Stages are chained by Pub/Sub: each one finishes by publishing a small JSON "batch ready" message that wakes the next one up.

Design thread running through everything

No stage ever pulls bulk rows into Python. Bronze streams a CSV straight into BigQuery by URI; every later stage submits SQL and reads back a handful of summary numbers. That's the only way this works at 42M–67M rows per file without a function running out of memory or timing out on a download.

Infrastructure — Terraform

Terraform (Terraform/modules/{storage,bigquery,service_account}) provisions the bucket, the three BigQuery datasets, the bare tables inside them, and the pipeline's one service account. It deliberately does not define any table's columns.

Terraform/modules/bigquery/main.tf
resource "google_bigquery_table" "raw_data" {
  dataset_id          = google_bigquery_dataset.analytics.dataset_id
  table_id            = "raw_data_table"
  deletion_protection = false
  // no schema block — columns are owned by the Python code, not Terraform
}

That last line is a recurring theme: every Cloud Function's tables.py exists specifically to patch a schema onto a table Terraform created empty. Whoever owns this project chose that split deliberately — schema lives with the transformation logic that depends on it, versioned in the same place, in the same language.

A real bug this caused

CREATE TABLE IF NOT EXISTS is a no-op on a table that already exists — even with zero columns. Both Silver and Gold hit this: the control tables stayed schemaless until the code was changed to check table.schema and call update_table() explicitly. fact_events needed an extra step — partitioning can't be added after creation, so a schemaless, un-partitioned placeholder gets dropped and recreated once, correctly this time.

Stage 1 · Bronze gcs_to_bronze Trigger: GCS object finalized on shopsense-data-lake

A CSV lands in the bucket. This function copies it, byte for byte, into raw_data_table — no cleaning, no type-casting, nothing dropped — then tells the next stage a file is ready.

main.pyorchestration only

Reads top-to-bottom like a table of contents for the other five files. Five steps: parse the event → skip if it's not our bucket/not a CSV → load the CSV → build the batch identity → publish. A SkipFile exception is a clean, expected exit (wrong file type); any other exception fails the function so Pub/Sub retries the event.

main.py — the batch identity
load_type = resolve_load_type(file_name)   # "historical/…" or "incremental/…" prefix
batch_id   = f"BATCH_{generation}"          # GCS's own version number — stable, unique per upload
gcs_event.pyunderstand + vet the event
FunctionDoes
parse_event()pulls bucket_name, file_name, generation out of the raw CloudEvent
validate_event()raises SkipFile unless it's a CSV in the right bucket
resolve_load_type()historical/ → HISTORICAL, incremental/ → INCREMENTAL, else UNKNOWN
bronze_loader.pythe actual load

The one function that matters: load_csv_to_bronze() hands BigQuery a gs:// URI directly — the file is never downloaded into the function. A fixed BRONZE_SCHEMA (from schemas.py) is used instead of autodetect, so column types can never silently drift between files, and event_time is loaded as STRING on purpose — parsing it into a real timestamp is Silver's job, not Bronze's.

job_config = bigquery.LoadJobConfig(
    source_format=bigquery.SourceFormat.CSV,
    skip_leading_rows=1,
    schema=BRONZE_SCHEMA,
    write_disposition=bigquery.WriteDisposition.WRITE_APPEND,  # ever-growing history
)
pubsub_publisher.pyhand off to Staging

publish_bronze_loaded() sends bucket_name, file_name, generation, batch_id, load_type, row_count to shopsense-bronze-loaded. It calls future.result() — blocks until Pub/Sub confirms — so a broker outage fails loudly instead of the function "succeeding" with nobody downstream ever hearing about it.

Stage 2 · Bronze→Staging bronze_to_staging Trigger: shopsense-bronze-loaded

Loads the same CSV a second time — this time into shopsense_raw_stg — and stamps four lineage columns onto every row: ingestion_timestamp, source_file_name, batch_id, load_type. This is the table Silver actually reads from.

main.pyorchestration + idempotency guard

The step that makes this whole function safe to retry: before doing any work, it checks ingestion_control for a SUCCESS row on this exact (bucket, file, generation). If found, it's a duplicate Pub/Sub delivery — log and return. start_processing() then claims the batch (PROCESSING), and only after the load succeeds does it flip to SUCCESS and publish onward.

ingestion_control.pythe retry state machine

One row per batch, moving through PROCESSING → SUCCESS (or FAILED, which a later retry flips back to PROCESSING). This exact pattern — a control table keyed on batch_id — repeats, expanded with more metric columns, in both Silver and Gold.

FunctionDoes
already_succeeded()true if this exact object generation already has a SUCCESS row
start_processing()claims the batch; returns SUCCESS (stop) or PROCESSING (ours to run)
finish()UPDATE ... WHERE status='PROCESSING' — only ever moves a row it owns
gcs.pyre-verify the file hasn't changed

verify_generation() re-fetches the GCS object pinned to the exact generation named in the message. If someone overwrote that path in between, the generation won't match and the function bails rather than load the wrong bytes.

staging_loader.pyCSV → temp table → staging

A two-step load: the CSV goes into a disposable, per-batch temp table that matches its 9 raw columns exactly, then one INSERT … SELECT copies those rows into staging while stamping the 4 metadata columns on via query parameters. The temp table is always dropped in main.py's finally block, success or failure.

INSERT INTO staging (event_time, …, ingestion_timestamp, source_file_name, batch_id, load_type)
SELECT event_time, …, @ingestion_timestamp, @source_file_name, @batch_id, @load_type
FROM temp_table

Stage 3 · Silver staging_to_silver Trigger: shopsense-staging-loaded

The cleaning stage: trims and normalises every column, removes exact duplicates, quarantines rows that fail a hard rule, and assigns each survivor a permanent, ever-increasing surrogate key. Everything below happens inside one BigQuery script — silver_sql.py builds the text, transform.py submits it once.

silver_sql.pythe transformation, as one script

Reads only the rows for the one incoming batch_id — never the whole staging table. Five moves, in order:

StepWhat happens
cleanTRIM, LOWER(event_type), NULLIF(x,'') on text fields, SAFE.PARSE_TIMESTAMP, CAST(price AS NUMERIC)
tageach row gets SESSION_MISSING / PRICE_ZERO / INVALID_TIMESTAMP or nothing
fingerprintrow_hash = SHA256 of the 9 cleaned columns, fixed order
dedupeROW_NUMBER() OVER (PARTITION BY row_hash) — copy 1 keeps, the rest are quarantined
key + mergeMAX(surrogate_key)+ROW_NUMBER(), then MERGE ... WHEN NOT MATCHED into Silver
the fingerprint — the whole basis of exact-duplicate detection
TO_HEX(SHA256(TO_JSON_STRING(STRUCT(
    c_event_time, c_event_type, product_id, category_id,
    c_category_code, c_brand, c_price, user_id, c_user_session
)))) AS row_hash

Two rows with identical cleaned values get the identical hash — regardless of which file, which position, which batch they came from. That's the entire duplicate-detection mechanism: a table-wide NOT EXISTS lookup on this string, never a positional comparison.

transform.pysubmit the script, read the metrics

run_transformation() is the only place BigQuery is actually called. It submits the script from silver_sql.py, blocks on .result(), and reads back one row of counts — source_rows, exact_duplicates_removed, price_zero_removed, session_missing_removed, invalid_timestamp_rows, rows_inserted, rows_skipped. No row-level data ever reaches Python.

control.pyingestion_transform_control state machine

Same PROCESSING→SUCCESS/FAILED pattern as Bronze's ingestion_control.py, with the metric columns above written on success — the audit trail for every batch Silver has ever touched.

Idempotency, precisely

Three independent guarantees stack up: (1) already_succeeded() stops a re-delivered message before it does anything; (2) the whole transform runs inside a BEGIN TRANSACTION, so a failure midway leaves Silver and quarantine untouched; (3) even if it ran twice anyway, the MERGE only inserts row_hash values Silver doesn't already have. Any one of the three would already prevent a duplicate.

Stage 4 · Gold silver_to_gold Trigger: shopsense-silver-loaded

Reshapes the clean Silver rows into a star schema — 6 small dimension tables plus one fact table — for analytics. Every run rebuilds every dimension from scratch and re-MERGEs against the whole Silver table; see the design notes below for exactly why that's safe.

gold_sql.pythe whole build, one script, 8 steps
#TableMethodKey idea
1dim_dateCREATE OR REPLACEone row per day, from GENERATE_DATE_ARRAY(MIN, MAX event_time)
2dim_categoryCREATE OR REPLACEexplode category_code into every prefix level; key = FARM_FINGERPRINT(path)
3bridge_category_hierarchyCREATE OR REPLACEWITH RECURSIVE closure table — every ancestor↔descendant pair
4dim_brandCREATE OR REPLACEdistinct brand + one UNKNOWN(-1) row
5dim_productCREATE OR REPLACEGROUP BY product_id, preferring a non-NULL category/brand from anywhere in the group
6dim_sessionCREATE OR REPLACEGROUP BY user_session — start/end time, event count, has_purchase, is_multi_user
7fact_eventsMERGEON event_key WHEN NOT MATCHED THEN INSERT — the one table that only ever grows
8metricsSELECTone row: row counts + FK-orphan check + duplicate-key check
why dim_category is keyed by category_code, never category_id
-- up to 23 different category_id values map to the SAME category_code text
-- ("apparel.shoes") — category_id is not 1:1 with the category. So:
FARM_FINGERPRINT(category_code) AS category_key   -- the key
-- category_id rides along in fact_events as a plain passthrough column,
-- never a foreign key.
the fact MERGE — reuses Silver's own surrogate_key as the identity
MERGE fact_events T
USING (
  SELECT CAST(s.surrogate_key AS STRING) AS event_key, …
  FROM silver s
  WHERE s.event_type IN ('view', 'cart', 'purchase')
) S
ON T.event_key = S.event_key
WHEN NOT MATCHED THEN INSERT (…)
build.pysubmit + read metrics

The Gold equivalent of Silver's transform.py — one call to client.query(sql), one row read back: silver_rows, dim_*_rows, fact_events_inserted, fact_events_total, fk_resolution_failures, duplicate_event_keys.

tables.pythe schema-retrofit + repartition trick

Handles the two tables that aren't rebuilt every run. ingestion_insight_control gets its schema patched on via update_table() if it's empty. fact_events is trickier — it needs PARTITION BY date_key, CLUSTER BY category_key, product_key, session_key, which can't be added after the fact. If it's a schemaless, un-partitioned Terraform placeholder, it's dropped and recreated correctly once — never touched again after that.

The bug this design almost hid

Truncating Silver resets its MAX(surrogate_key) back to zero, so a reloaded file's new rows get recycled event_key values — ones that already exist in an untouched fact_events. The MERGE then (correctly, by its own logic) treats them as already-loaded and inserts nothing. Not a MERGE bug — a violation of the assumption that a surrogate key is never reused. Lesson: truncate Silver and Gold together, never one without the other.

16 standalone CREATE OR REPLACE VIEW files, one per file, deployed by deploy_views.ps1 (it auto-discovers every vw_*.sql, so a new file needs no script change). None of them create a new physical table — they're saved queries over fact_events and the dimensions.

Every view follows the same shape

Aggregate fact_events down to the target grain in a CTE first, then join to the (tiny) dimension tables — so a join can never multiply fact rows, and any window function (RANK, PERCENT_RANK, NTILE) runs on the small aggregated result, never the raw fact table. Every rate uses SAFE_DIVIDE — a zero denominator returns NULL, never an error or a false 0%/100%.

Two patterns worth understanding in depth

vw_brand_engagement_conversion.sqlpercentile thresholds, not magic numbers

"High" and "low" are never hardcoded. PERCENT_RANK() sorts every brand by a metric and reports, for each one, what fraction of the group sits at or below it — always 0 to 1, recomputed fresh on every run regardless of how the dataset grows.

PERCENT_RANK() OVER (ORDER BY engagement) AS engagement_percentile,
PERCENT_RANK() OVER (ORDER BY SAFE_DIVIDE(purchases, engagement)) AS conversion_percentile
…
(engagement_percentile >= 0.75 AND conversion_percentile <= 0.25) AS is_high_engagement_low_conversion

Both raw percentiles ship as columns, so the 0.75 / 0.25 cutoff is auditable and adjustable without re-deriving anything.

vw_dashboard_overview.sqlthe hierarchy-denormalisation + INT64-overflow fix

Events are tagged at the category leaf (e.g. electronics.audio.headphone), so filtering on "Electronics" would match almost nothing. A category_path CTE resolves each leaf's level-1/2/3 ancestor names once from bridge_category_hierarchy — grouped to exactly one row per category_key, so the join can't duplicate rows — and denormalises them onto every fact row instead.

-- FARM_FINGERPRINT ids are huge signed integers. Left as INT64, Looker Studio
-- auto-classifies them as a metric and tries to SUM them → integer overflow.
CAST(a.category_key AS STRING) AS category_key   -- forces it to be treated as a label

A good example of a mechanism (hash keys) having a consequence its designers hadn't needed to think about until a specific consumer — Looker Studio's auto-typing — met it.

Key concepts glossary

The handful of ideas that repeat across every stage. Understand these five and the rest of the codebase reads as applications of them.

row_hash

SHA256 of Silver's 9 cleaned columns. Identical values → identical hash, regardless of file, batch, or row position. The entire basis of exact-duplicate detection when there's no natural key in the source data.

surrogate_key

Silver's plain 1, 2, 3… counter, computed as MAX(existing) + ROW_NUMBER() — keeps counting across every file, never restarts. Reused directly as Gold's event_key (cast to STRING).

FARM_FINGERPRINT

Turns a text value into the same 64-bit integer every time. Makes Gold's dimensions safe to drop and rebuild on every run — the key is a pure function of the value, so it never changes and never needs coordination.

MERGE … WHEN NOT MATCHED

"Insert this row only if it isn't already there." The one idempotency mechanism that matters for anything that appends (Silver's transform, Gold's fact_events) — rebuilt tables don't need it at all.

ingestion_*_control

One row per batch, PROCESSING → SUCCESS / FAILED, repeated with growing metric columns at Bronze, Silver, and Gold. The audit trail and the retry guard, in one table.

star schema

Dimensions are the "nouns" (product, category, day, session) — small, descriptive, rebuilt freely. The fact is one narrow row per event, holding only number keys plus measures — big, fast to aggregate.

SAFE_DIVIDE

Every rate in every view uses it. A zero denominator returns NULL (genuinely undefined) instead of crashing the query or faking a 0%/100%.

-1 (UNKNOWN)

The one hardcoded sentinel key, for category_key/brand_key when the source value was NULL. Every other negative key is just an ordinary hash output — sign and magnitude carry no meaning beyond equality.
